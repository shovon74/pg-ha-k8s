# Security baseline

What the cluster protects, how, and what it leaves out (R8.1). The decision is [ADR-012](decisions/ADR-012-security-baseline.md): a layered baseline, built last. Evidence: [`evidence/L6-security.md`](evidence/L6-security.md), generated by `make test-security`. Hand-written notes: [`evidence/L6-security-history.md`](evidence/L6-security-history.md).

## Implemented

| Area | What | R-ID | Proof (`make test-security` unless noted) |
|---|---|---|---|
| Credentials | Every password, token and key is generated at deploy time by `make secrets` (`openssl rand`) into `./secrets` (git-ignored, mode 0700). Each is loaded into a Kubernetes Secret with server-side apply, so no value lands in a last-applied annotation. Scripts never print a value. Evidence files pass through automatic redaction (`[REDACTED:<name>]`) | R8.2, R8.3 | Full-history scan: no current credential value, and no private-key block, appears in `git log -p --all` or the tracked tree |
| TLS, clients | Postgres runs TLS with the L0 deployment CA certificate (`make certs`), at TLS 1.2 or newer. Every connection from the pod network must use TLS: `pg_hba` allows `hostssl` only, and ends in explicit `host ... reject` lines. The server certificate covers `pg-rw`, `pg-ro` and every `pg-N.pg-headless` name in `pg-ha` and `pg-restore`, so clients can use `sslmode=verify-full` | R8.4 | `sslmode=verify-full` through pg-rw and pg-ro shows TLS 1.3 in `pg_stat_ssl`. `sslmode=disable` is refused by `pg_hba` ("no encryption") |
| TLS, replication | Patroni connects for streaming, `pg_basebackup` re-clone and the rewind role's divergence check with `sslmode=verify-full` and `sslrootcert` set to the L0 CA, so each replica verifies the primary's name and certificate | R8.4 | Both streams show `ssl=true` on the primary. Each replica's `pg_stat_wal_receiver.conninfo` shows `sslmode=verify-full` and the CA path |
| TLS, pgBackRest | Since L3, Jobs reach each member's pgBackRest TLS server on 8432 with a client certificate, authorised by CN (`tls-server-auth`). The server verifies the client, and the client verifies the server | ADR-009 | `pgbackrest check` from a backup-template Job |
| Authentication | SCRAM-SHA-256 for every password login (`password_encryption=scram-sha-256`, every `pg_hba` method `scram-sha-256`). The superuser cannot log in over the network at all, because a reject rule comes before the general rule. Patroni, `post_bootstrap` and pgBackRest use the local socket. Loopback (`127.0.0.1/32`) stays `host` with SCRAM for the exporter sidecar (which uses `sslmode=require` anyway) and Patroni's local replication check. That traffic never leaves the pod | R8.5 | A wrong password is refused. A remote `postgres` login is refused by `pg_hba` before any password exchange |
| Database roles | Separate roles per purpose: `postgres` (superuser, local only), `replicator` (REPLICATION only), `rewind` (no attributes), `monitor` (`pg_monitor`), `backup` (`pg_checkpoint`, `pg_read_all_settings`), `app` (owns database `app`), `app_ro` (`pg_read_all_data`). PG 15+ defaults keep `CREATE` on `public` from everyone but the owner | R8.5 | Role matrix from `pg_roles`. `app` cannot open a physical replication connection (`pg_hba`), cannot start a WAL sender, and cannot create roles. `app_ro` and `monitor` cannot create tables. `app_ro` can read |
| Patroni REST API | HTTP basic auth for every state-changing request (POST, PUT, PATCH, DELETE: switchover, failover, restart, reinitialize, config). GET stays open, so kubelet probes, Prometheus `/metrics`, `make status` and the `patroni_cluster` helper are unchanged. User `patroni`, with the password from `pg-credentials` (`pg-restapi-password`). The switchover harness reads it from `./secrets` and gives it to curl on stdin (`-K -`), never on a command line | ADR-012 | Unauthenticated or wrong-password `POST /switchover`, `POST /restart`, `POST /reinitialize`, `PATCH /config` and `DELETE /switchover` all return 401. An authenticated scheduled switchover returns 202 and is then cancelled (200). `make switchover` runs a real authenticated switchover |
| NetworkPolicy | Default deny for ingress and egress in `pg-ha` (Postgres and Garage), `monitoring` and `monitoring-host`, then one allow per real path (table below). The API backend address and the server node's proxy source addresses are discovered live by `scripts/netpol.sh`, never hard-coded | R8.6 | A pod in another namespace, labelled to look like a member and a client, is rejected on 5432 (pod IP and pg-rw), 8008, 8432, 9187, Garage 3900 and 3903, and Prometheus 9090, while its DNS works. The test client reaches 5432 only. Every allowed path still works |
| Pod Security | `pg-ha` and `monitoring` enforce, warn and audit at `restricted`. Every container runs non-root with `RuntimeDefault` seccomp, no privilege escalation, all capabilities dropped and a read-only root filesystem. The one exception is `monitoring-host` (node_exporter, read-only `hostPath`), which enforces `privileged` and warns and audits at `restricted` (ADR-011) | R8.7 | Server-side re-check of both namespaces gives no warning. A privileged pod and a pod without a restricted securityContext are rejected. A compliant pod is admitted |
| RBAC | Namespaced Roles only. No ClusterRole or ClusterRoleBinding is created for any project ServiceAccount (matrix below). Pods that need no API access mount no token | R8.8 | `kubectl auth can-i --list` per ServiceAccount, and 33 can-i checks (positives and negatives) |
| Backup content | The pgBackRest repository is encrypted (`aes-256-cbc`, passphrase in Secret `pgbackrest-repo`), and S3 requests are SigV4-signed, so the secret key never crosses the wire | ADR-009, ADR-014 | L3 evidence. Raw-object unreadability is not tested (R8.10, optional) |

### NetworkPolicy paths

Everything not listed is denied. DNS (UDP and TCP 53 to CoreDNS) is allowed for every pod in `pg-ha` and `monitoring`. `monitoring-host` has no egress at all.

| From | To | Port | Why |
|---|---|---|---|
| Postgres members | Postgres members | 5432, 8008 | Replication, re-clone, Patroni leader race (`GET /patroni`) |
| Postgres members | Garage | 3900 | `archive-push`, `archive-get` |
| Postgres members | API server backend (discovered) | 6443 | Patroni's Kubernetes DCS |
| `pg-ha/db-client=true` pods in `pg-ha`, or in a namespace with that label | Postgres members (pg-rw, pg-ro) | 5432 | Database clients: test client, write probe, seed Job, backup Job (fingerprint), applications |
| Backup Job (and stanza and check helpers) | Postgres members | 8432, 5432 | pgBackRest TLS server, fingerprint query |
| Backup and restore-test Jobs, any pod in `pg-restore` | Garage | 3900 | Repository reads and writes, `make restore` |
| Garage bootstrap Job | Garage | 3903 | Admin API |
| Prometheus | Postgres members | 8008, 9187 | Patroni `/metrics`, postgres_exporter |
| Prometheus | node_exporter (`monitoring-host`) | 9100 | Node metrics |
| Prometheus | kube-state-metrics, Alertmanager | 8080, 8081, 9093 | Scrape and alert delivery |
| Prometheus, kube-state-metrics | API server backend (discovered) | 6443 | Pod discovery, list and watch |
| Server node (InternalIP, flannel tunnel and cni0 addresses, discovered) | Postgres 8008, Prometheus 9090, Alertmanager 9093 | | API server pod and service proxy: `make status`, `make alerts`, `make monitoring`, tests |

Kubelet probes come from the pod's own node, which kube-router always allows. `kubectl port-forward` enters the pod's network namespace directly, so policies do not apply to it. It needs `pods/portforward`, which only cluster admins have. The restored cluster in `pg-restore` gets no policies (below).

### RBAC matrix

| ServiceAccount | Binding | Can do | Cannot do (tested) |
|---|---|---|---|
| `pg-ha/pg` (Patroni) | Role `pg-patroni` in `pg-ha` | Endpoints: all verbs (leader lock, config, sync and failover keys). Pods: get, list, watch, update, patch (member annotations, role label). Services: create (Patroni's `pg-rw-config` Service) | Secrets, ConfigMaps, creating or deleting pods, `pods/exec`, `pods/portforward`, updating Services, StatefulSets, RoleBindings, any other namespace, nodes, namespaces |
| `monitoring/prometheus` | Role `prometheus-sd` in `pg-ha` and `monitoring-host` | Pods: get, list, watch | Secrets, pods in other namespaces, creating pods, nodes |
| `monitoring/kube-state-metrics` | Role `kube-state-metrics` in `pg-ha` and `kube-system` | Jobs, CronJobs, StatefulSets, Deployments: list, watch | Secrets, pods, other namespaces, nodes |
| `default` in each namespace | none | Nothing beyond the built-in discovery and OIDC endpoints that every authenticated identity has | Pods, Secrets |

Garage, Alertmanager, node_exporter and every Job set `automountServiceAccountToken: false`. The test client, probe and seed pods mount the `default` token, which has no permissions. **No ClusterRole is used.** Patroni's `endpoints: delete` and `services: create` are what its Kubernetes DCS needs with `use_endpoints` (ADR-002).

## Credential inventory

Every value is generated by `make secrets` or `make certs`, kept in `./secrets` on the host, and never committed. "Consumers" lists every pod that can read the value.

| File in `./secrets` | Kubernetes Secret / key | Consumers | Purpose |
|---|---|---|---|
| `credentials/pg-postgres-password` | `pg-credentials` / same name | Postgres pods (Patroni) | Superuser. Local socket only, since remote login is rejected by `pg_hba` |
| `credentials/pg-replicator-password` | `pg-credentials` | Postgres pods | Streaming replication and re-clone, over TLS with verify-full |
| `credentials/pg-rewind-password` | `pg-credentials` | Postgres pods | Divergence check before re-clone (ADR-008) |
| `credentials/pg-monitor-password` | `pg-credentials` | Postgres pods (exporter sidecar), test client | `monitor` role (`pg_monitor`) |
| `credentials/pg-backup-password` | `pg-credentials` | Postgres pods (`post_bootstrap` only) | `backup` role. **Not used for logins today:** pgBackRest connects as the superuser over the local socket through its TLS server. Kept for a future non-superuser backup setup |
| `credentials/pg-app-password` | `pg-credentials` | Postgres pods (`post_bootstrap`), test client, write probe, seed and API-outage Jobs | Application role `app` |
| `credentials/pg-app_ro-password` | `pg-credentials` | Postgres pods (`post_bootstrap`), **backup Job** (read-only data fingerprint, `fingerprint.sql`), test client | Read-only role `app_ro`. The backup Job gets only this database credential. It cannot write, replicate or log in as anyone else |
| `credentials/pg-restapi-password` | `pg-credentials` | Postgres pods (Patroni). Read on the host by `tests/failover.sh switchover` and `tests/test-security.sh` | Basic auth for Patroni's state-changing REST endpoints (L6) |
| `credentials/pgbackrest-cipher-passphrase` | `pgbackrest-repo` / `PGBACKREST_REPO1_CIPHER_PASS` | Postgres pods, backup, stanza, check and restore-test Jobs, restored cluster in `pg-restore` | Repository encryption key. Losing it makes every backup unreadable |
| `credentials/garage-s3-access-key-id`, `garage-s3-secret-key` | `pgbackrest-repo` / `PGBACKREST_REPO1_S3_KEY`, `..._KEY_SECRET` | Same as the passphrase, plus the Garage bootstrap Job (imports the key) | S3 access to the `pgbackrest` bucket only |
| `credentials/garage-rpc-secret` | `garage` / `GARAGE_RPC_SECRET` | Garage | Garage node RPC (single node) |
| `credentials/garage-admin-token` | `garage` / `GARAGE_ADMIN_TOKEN` | Garage, Garage bootstrap Job | Admin API v2 (layout, key, bucket) |
| `credentials/garage-metrics-token` | `garage` / `GARAGE_METRICS_TOKEN` | Garage | Metrics endpoint token. Garage is not scraped today |
| `tls/ca.key` | none | Host only (`make certs`) | Signs the deployment certificates. **Never enters the cluster** |
| `tls/ca.crt` | `pg-tls` / `ca.crt`, `pgbackrest-tls` / `ca.crt` | Postgres pods, backup Jobs, test client (this key only, mounted by `items`) | Trust anchor for verify-full and pgBackRest TLS |
| `tls/postgres-server.{crt,key}` | `pg-tls` / `tls.crt`, `tls.key` | Postgres pods (mode 0440, group 999) | Postgres server certificate |
| `tls/pgbackrest-server.{crt,key}`, `tls/pgbackrest-client.{crt,key}` | `pgbackrest-tls` | Postgres pods (server), backup, stanza and check Jobs (client) | pgBackRest TLS server and its client certificate (CN `pgbackrest-client`) |

`scripts/restore.sh` copies `pg-credentials`, `pg-tls`, `pgbackrest-tls` and `pgbackrest-repo` into `pg-restore` for the temporary restored cluster. `.run/kubeconfig` (cluster admin, created by k3d) stays on the host and is git-ignored.

## Left out, and why

| Not implemented | Why | What production would do |
|---|---|---|
| **Client certificate authentication** for application roles | Passwords with SCRAM over verified TLS meet the brief. Client certificates add per-client issuance and rotation, which in this design would be manual openssl work | `hostssl ... cert` (or `scram-sha-256 clientcert=verify-full`) with certificates from an internal CA |
| **Secret rotation tooling** | Out of scope for the time box (ADR-012 "full hardening"). Rotation today is manual: replace the file in `./secrets`, re-run `make deploy`, and reset the role password (the restore path already does this in `post_bootstrap`). The S3 key was rotated once this way in L0 | An external secret store (Vault, a cloud secret manager) with scheduled rotation, and workload identity for object storage |
| **Image vulnerability scanning** (R8.9, optional) | Optional, and it needs a scanner and its vulnerability database. Images are pinned by digest, which makes a later scan reproducible | Trivy or Grype in CI against the pinned digests, with a triage note per finding |
| **TLS for Garage S3** | Garage has no native TLS (ADR-014). The repository is encrypted and SigV4 keeps the secret key off the wire, but S3 metadata (object names, sizes) crosses the pod network in clear, and only NetworkPolicy limits who can reach it | A TLS-terminating proxy sidecar, or an off-site GCS/S3 repository over HTTPS (R4.7) |
| **cert-manager** | It is an operator (constraint D1) | cert-manager or a cloud CA, with automatic renewal. Today's certificates come from `make certs` and are valid for 825 days |
| **TLS on the Patroni REST API** | Basic auth protects every state-changing call, and NetworkPolicy limits who can reach port 8008 (members, Prometheus, the API server proxy). The credential travels in clear only on the pod network or through a port-forward tunnel. TLS would also mean changing the probes, the scrape job and the proxy-based helpers | `restapi.certfile`, `keyfile` and `cafile`, with HTTPS probes and scrapes |
| **Encryption of Kubernetes Secrets at rest** | k3s's `--secrets-encryption` changes the cluster bootstrap (ADR-001). Its etcd/kine store sits on the same single VM as `./secrets` | Envelope encryption with a KMS provider |
| **NetworkPolicies and Pod Security labels in `pg-restore`** | The restored cluster is temporary, holds a copy of production data, and is deleted by `make restore-clean`. `scripts/restore.sh` creates the namespace without Pod Security labels, although its pods come from the same restricted-compliant manifests. Policies would have to be rendered per restore | Label the namespace `restricted` and render the same policies for it, or restore into an isolated cluster |
| **API server audit policy** | Needs k3s server flags and log handling outside the time box | An audit policy for Secrets, exec, port-forward and RBAC changes, shipped off the node |
| **Raw-bucket proof of backup encryption** (R8.10, optional) | Optional. Encryption is on (above), but the test that raw objects are unreadable without the key was not written | Read a raw object from Garage and show it does not decrypt |

The node itself is out of scope: k3d runs each Kubernetes node as a privileged Docker container on one VM (ADR-001). Container isolation here protects workloads from each other, not the host from the cluster.
